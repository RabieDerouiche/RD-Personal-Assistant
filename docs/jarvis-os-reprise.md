## Ce qu'est JARVIS OS (16/11/2026)

L'assistant personnel du propriétaire sur iPhone : une app web (installable sur l'écran d'accueil) servie par **son propre serveur**, qui remplace la page Jarvis de claude.ai. Pas de frais d'API : Claude passe par son abonnement (Claude Code sur le serveur), les données Google par un accès Google direct qu'il a créé lui-même.

## Le serveur

- VPS OVH (VPS-1, Ubuntu 26.04), adresse `https://<ip-avec-tirets>.sslip.io` (exacte : Google Doc privé, ou le mail OVH « Installation de votre VPS »).
- Service systemd `jarvis` (utilisateur `jarvis`), dépôt cloné dans `/opt/rd`, données dans `/home/jarvis/.jarvis/state.json` (droits 600 : jetons des appareils en empreinte, identifiant et secret Google, jeton Google, mémoire, missions). Caddy en façade (HTTPS automatique).
- **Mettre en ligne une modification** (0.27.0, comme Panier) : fusionner dans `main`, et c'est tout. À l'ouverture de JARVIS (une seule vérification, au lancement), l'app propose « Nouvelle version disponible » : « Plus tard » ou « Mettre à jour » ; sur oui, le serveur fait `git pull --ff-only`, systemd le relance, l'app attend le nouveau code et se recharge seule. Seuls les fichiers de l'app et du serveur déclenchent la question (pas la documentation). Réglages, « Mettre à jour le serveur », force la vérification. `JARVIS_MAJ=0` dans le service coupe ce mécanisme. En SSH : `sudo -u jarvis git -C /opt/rd pull --ff-only && sudo systemctl restart jarvis`. **Règles à garder** : pas de `skipWaiting()` à l'installation dans `sw.js` ; ne pas retirer le filet de sécurité du début de `index.html`.
- **Dépôt en privé** (son choix, QCM du 21/11/2026 ; à faire par lui, pas encore fait le 22/11/2026). Le serveur se met à jour depuis GitHub sans clé : passé en privé sans préparation, « Mettre à jour » échouerait. Dans l'ordre : (1) faire la mise à jour en attente ; (2) dans sa session « Serveur JARVIS », créer une clé de déploiement pour l'utilisateur `jarvis` (`/home/jarvis/.ssh/id_ed25519`, sans phrase de passe ; `github.com` ajouté à `known_hosts`) ; (3) dans GitHub, Settings du dépôt, Deploy keys, ajouter sa clé publique, en lecture seule ; (4) `sudo -u jarvis git -C /opt/rd remote set-url origin git@github.com:RabieDerouiche/RD-Personal-Assistant.git` puis `sudo -u jarvis git -C /opt/rd fetch` (aucune erreur attendue) ; (5) seulement alors, Settings, General, Danger Zone, Change visibility, Make private ; (6) dans JARVIS, Réglages, « Mettre à jour le serveur » : doit répondre « Déjà à jour ». Effet de bord : avec un compte GitHub gratuit, GitHub Pages ne publie plus rien (il exige un dépôt public ou une offre payante) ; les maquettes sont servies par le serveur depuis 0.53.0 (ci-dessous). Même méthode que Panier (`docs/panier.md` de son dépôt).
- **Nouvelle installation, dépôt privé** (serveur neuf ou réinstallé, une fois le dépôt en privé). La ligne `curl … raw.githubusercontent.com … | sudo bash` et `install/cloud-config.yaml` ne marchent plus (404). `setup.sh` clonerait en HTTPS sans clé, et s'arrêterait. Il garde un utilisateur `jarvis` et un `/opt/rd/.git` déjà là (il fait alors `git pull` en `jarvis`) : il suffit de cloner avant de le lancer. Dans l'ordre, en SSH (Termius) : (1) `sudo useradd -m -s /bin/bash jarvis` ; (2) `sudo -u jarvis install -d -m 700 /home/jarvis/.ssh`, `sudo -u jarvis ssh-keygen -t ed25519 -N '' -f /home/jarvis/.ssh/id_ed25519`, puis `sudo -u jarvis sh -c 'ssh-keyscan github.com >> /home/jarvis/.ssh/known_hosts'` ; (3) le propriétaire ajoute la clé publique (`sudo cat /home/jarvis/.ssh/id_ed25519.pub`) dans GitHub, Settings du dépôt, Deploy keys, en lecture seule (« Allow write access » décoché) ; (4) `sudo apt-get install -y git`, `sudo install -d -o jarvis -g jarvis /opt/rd`, puis `sudo -u jarvis git clone --depth 1 git@github.com:RabieDerouiche/RD-Personal-Assistant.git /opt/rd` ; (5) `sudo bash /opt/rd/jarvis-os/server/install/setup.sh`, à la place de la ligne `curl` ; puis la suite habituelle (`claude auth login`, code d'appairage : `docs/jarvis-os.md`, choix OVHcloud VPS-1). Procédure écrite le 23/11/2026, pas encore essayée sur un vrai serveur.
- **Un proche envoie des tâches** (0.62.0 ; message vocal et rappels toutes les 5 minutes depuis la 0.64.0) : sa page est `https://<serveur>/invite/` (lien d'invitation créé dans Réglages, carte « Tâches envoyées par un proche »). **Règle à garder** : la clé d'un invité n'ouvre que `POST /api/invite/tache`, `POST /api/invite/vocal` et `GET /api/invite/taches` ; jamais une autre adresse, jamais une donnée de JARVIS hors du statut de ses propres tâches. Ses messages vocaux restent sur le serveur, tels qu'elle les a envoyés (`~/.jarvis/invites/`, 7 jours, jamais transcrits depuis la 0.67.0) ; seule la clé du Raccourci du propriétaire (ou un appareil relié) lit le dernier (`GET /api/raccourci/vocal`) et relaie ses messages de Messages (`POST /api/raccourci/message` : un son devient une tâche, un texte est ignoré et jamais gardé). Le m4a de l'iPhone est lu par PyAV, installé avec l'écoute (`stt/audio_helper.py`) ; sans l'écoute, sa page lui fait ajouter « Encoder le média » (AIFF). Le service worker ignore `/invite` (exclusion à garder dans `essais/jarvis-os-maquette/sw.js`). Depuis la 0.70.0, la clé reste dans l'adresse après « # » (jamais envoyée au serveur), pour que l'icône posée sur son écran d'accueil s'ouvre avec sa clé.
- **Maquettes** (0.53.0, son choix du 22/11/2026 : « Sur ton serveur ») : servies par le serveur, plus par GitHub Pages. `https://<serveur>/maquettes/` donne la liste, `https://<serveur>/maquettes/ux/` la refonte UX (`essais/jarvis-os-ux/`). Nouvelle maquette : une entrée dans `MAQUETTES` de `jarvis-os/server/server.mjs` (son dossier `essais/<dossier>/` entre dans `MAJ_CHEMINS`, donc « Nouvelle version disponible » le propose) ; elle est en ligne après « Mettre à jour ». Données inventées seulement : l'adresse est ouverte à qui la connaît (non indexée). Le service worker de JARVIS ignore `/maquettes` (exclusion à garder dans `essais/jarvis-os-maquette/sw.js`). L'adresse du serveur est dans le Doc privé de reprise, jamais dans le dépôt.
- **Administration du serveur** (depuis le 16/11/2026) : session « Serveur JARVIS » de l'app Claude (onglet Code ; Remote Control, service `jarvis-rc`, root, accord demandé à chaque commande). Une session de développement tourne dans le cloud sur le dépôt, jamais dans l'environnement « Serveur JARVIS » : elle ne touche pas au serveur, elle fusionne dans `main` ; depuis 0.27.0, JARVIS propose la mise à jour à sa prochaine ouverture.
- **Relier un téléphone** : `sudo -iu jarvis node /opt/rd/jarvis-os/server/server.mjs pair` affiche un code (30 min, usage unique), à saisir dans Réglages. **Retirer un appareil** (téléphone perdu, ancienne installation ; 0.70.0) : depuis un autre appareil relié, Réglages, carte « Serveur JARVIS », « Retirer » ; plus besoin d'éditer `state.json`. Si le seul appareil est perdu : en relier un nouveau avec un code, puis retirer l'ancien depuis le nouveau. S'il avait le raccourci « Jarvis », recréer aussi sa clé (Réglages, « Siri et bouton Action », « Recréer la clé »). « Délier cet iPhone » retire aussi sa clé du serveur.
- Claude Code sur le serveur est connecté à l'abonnement du propriétaire (`sudo -iu jarvis claude auth login` si besoin). Aucune clé d'API : les variables payantes sont retirées à chaque appel.
- `/courses…` n'est plus à JARVIS : Caddy l'envoie au service `panier` (port 8790), l'app Panier, qui a son propre dépôt (`Panier`) et sa propre mise à jour. Si `install/setup.sh` de JARVIS est relancé, il réécrit le Caddyfile : relancer ensuite `install/setup.sh` de Panier. Adresses servies par JARVIS : `/` nouvelle app, `/ancienne/` ancienne PWA, `/os/` redirigée vers `/` (301), `/invite/` page d'un proche, `/maquettes/` maquettes, `/api/*` (voir `jarvis-os/server/README.md`), `/confidentialite.html` (déclarée à Google, à ne pas déplacer).

## L'accès Google direct (créé par le propriétaire le 16/11/2026)

- Projet Google Cloud « JARVIS » du compte de Pilotage ; Google Auth Platform : type Externe, **publiée** en production (sinon le jeton expire en 7 jours), Branding sans logo (un logo impose une vérification), page d'accueil `https://<serveur>/`, confidentialité `https://<serveur>/confidentialite.html`, domaine autorisé `sslip.io`. Client OAuth « Application Web », redirection `https://<serveur>/api/google/callback`.
- L'identifiant et le secret ont été collés par lui dans Réglages : ils ne sont que sur le serveur. **Ne jamais les demander.** S'il faut reconnecter : Réglages, « Reconnecter ».
- Outils traduits (`google.mjs`) : Sheets `get_values`, `append_values`, `update_values` ; Calendar `list_events`, `create_event`, `update_event`, `delete_event` ; Gmail `search_threads`, `get_thread`, `list_drafts`, `send_message`, `delete_draft`, `unlabel_thread`. Depuis 0.11.0 : « Confier à la tâche Claude » (`fire_trigger`) fait par le serveur lui-même, sans clé (il lit les lignes « Pour = Claude » du Canal, Claude rédige sans outil, le serveur n'écrit que Réponse et Statut) ; outils de Claude dans la discussion de la page (`preparer_ordre`, `ajouter_tache`, `ajouter_echeance`, `confier_tache_claude`, `mettre_a_jour_dossier`) par des propositions en fin de réponse que le pont `jarvis-serveur.js` passe à la page (un seul appel, rien ne part sans son bouton). Depuis 0.10.1 : Drive `folder_tree` (lecture seule, arborescence d'un dossier, pour l'écran Papiers). Depuis 0.19.0 : « Revérifie dans mes papiers / mes mails » (`POST /api/verifier`) : le serveur cherche, Claude juge ; s'il y a du nouveau, le serveur écrit une ligne pour le bot dans le Canal et le sonne (seules écritures, faites par le serveur, pas par Claude).
