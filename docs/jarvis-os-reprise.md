## Ce qu'est JARVIS OS (16/11/2026)

L'assistant personnel du propriétaire sur iPhone : une app web (installable sur l'écran d'accueil) servie par **son propre serveur**, qui remplace la page Jarvis de claude.ai. Pas de frais d'API : Claude passe par son abonnement (Claude Code sur le serveur), les données Google par un accès Google direct qu'il a créé lui-même.

## Le serveur

- VPS OVH (VPS-1, Ubuntu 26.04), adresse `https://<ip-avec-tirets>.sslip.io` (exacte : Google Doc privé, ou le mail OVH « Installation de votre VPS »).
- Service systemd `jarvis` (utilisateur `jarvis`), dépôt cloné dans `/opt/rd`, données dans `/home/jarvis/.jarvis/state.json` (droits 600 : jetons des appareils en empreinte, identifiant et secret Google, jeton Google, mémoire, missions). Caddy en façade (HTTPS automatique).
- **Mettre en ligne une modification** (0.27.0, comme Panier) : fusionner dans `main`, et c'est tout. À l'ouverture de JARVIS (une seule vérification, au lancement), l'app propose « Nouvelle version disponible » : « Plus tard » ou « Mettre à jour » ; sur oui, le serveur fait `git pull --ff-only`, systemd le relance, l'app attend le nouveau code et se recharge seule. Seuls les fichiers de l'app et du serveur déclenchent la question (pas la documentation). Réglages, « Mettre à jour le serveur », force la vérification. `JARVIS_MAJ=0` dans le service coupe ce mécanisme. En SSH : `sudo -u jarvis git -C /opt/rd pull --ff-only && sudo systemctl restart jarvis`. **Règles à garder** : pas de `skipWaiting()` à l'installation dans `sw.js` ; ne pas retirer le filet de sécurité du début de `index.html`.
- **Dépôt en privé** (son choix, QCM du 21/11/2026 ; à faire par lui, pas encore fait le 22/11/2026). Le serveur se met à jour depuis GitHub sans clé : passé en privé sans préparation, « Mettre à jour » échouerait. Dans l'ordre : (1) faire la mise à jour en attente ; (2) dans sa session « Serveur JARVIS », créer une clé de déploiement pour l'utilisateur `jarvis` (`/home/jarvis/.ssh/id_ed25519`, sans phrase de passe ; `github.com` ajouté à `known_hosts`) ; (3) dans GitHub, Settings du dépôt, Deploy keys, ajouter sa clé publique, en lecture seule ; (4) `sudo -u jarvis git -C /opt/rd remote set-url origin git@github.com:RabieDerouiche/RD-Personal-Assistant.git` puis `sudo -u jarvis git -C /opt/rd fetch` (aucune erreur attendue) ; (5) seulement alors, Settings, General, Danger Zone, Change visibility, Make private ; (6) dans JARVIS, Réglages, « Mettre à jour le serveur » : doit répondre « Déjà à jour ». Effet de bord : avec un compte GitHub gratuit, GitHub Pages ne publie plus rien (il exige un dépôt public ou une offre payante) ; les maquettes sont servies par le serveur depuis 0.53.0 (ci-dessous). Même méthode que Panier (`docs/panier.md` de son dépôt).

## Pilotage hébergé par JARVIS (0.88.0, son choix du 26/11/2026)

Une fois basculé, Pilotage n'est plus dans Google : il est dans `/home/jarvis/.jarvis/pilotage.json` (600) et le classeur « Pilotage Grok Bot » est une archive figée. Le détail : `docs/jarvis-os.md`, entrée 0.88.0.
- **Mode** : la ligne `Environment=JARVIS_PILOTAGE=local` du fichier `/etc/systemd/system/jarvis.service.d/pilotage.conf` (puis `systemctl daemon-reload` et redémarrage). Sans ce fichier, JARVIS relit Google comme avant.
- **Commande** (sous jarvis) : `sudo -iu jarvis node /opt/rd/jarvis-os/server/server.mjs pilotage etat | importer [--a-blanc] [--forcer] | verifier | exporter [--a-blanc] [--tout] | cle | restaurer <fichier> | --drive [AAAA-MM-JJ] [--forcer] | copie`. Elle ne lit `state.json` que pour l'accès Google et n'affiche que des comptes et des dates. `importer` est refusé une fois que JARVIS a servi (il écraserait ses écritures), sauf `--forcer` service arrêté ; l'ancien magasin est gardé à côté (`pilotage.json.avant-…`).
- **Copies** : chaque nuit sur le serveur (30 jours, `sauvegardes/`), puis une copie chiffrée dans Drive (« Sauvegardes JARVIS », 30 copies). La phrase de passe est la sienne : `pilotage cle`, tapée par lui dans Termius (refusée par un tube, donc par la session du serveur) ; il la garde dans son gestionnaire de mots de passe. Sans elle, les copies de Drive sont illisibles. Il faut aussi la portée `drive.file` : Réglages, Google, « Reconnecter », tout cocher (sinon la santé dit « à relier » ; tout le reste marche).
- **Restaurer** (magasin perdu ou abîmé : la santé le dit, plus rien n'est lu ni écrit) : `sudo systemctl stop jarvis`, puis lui dans Termius `sudo -iu jarvis node /opt/rd/jarvis-os/server/server.mjs pilotage restaurer --drive` (la dernière copie ; ou `--drive AAAA-MM-JJ`, ou `restaurer <fichier>` pour une copie `.jarvis` téléchargée), sa phrase, `--forcer` si un magasin abîmé est encore là (il est gardé à côté), puis `sudo systemctl start jarvis`. Les copies en clair de la nuit (`~/.jarvis/sauvegardes/`) servent à voir ce qui a changé, pas à restaurer.
- **Retour arrière vers Google** : `sudo systemctl stop jarvis` ; `sudo -iu jarvis node /opt/rd/jarvis-os/server/server.mjs pilotage exporter` (les onglets changés depuis l'import réécrits dans le classeur ; `--a-blanc` d'abord) ; `sudo rm /etc/systemd/system/jarvis.service.d/pilotage.conf && sudo systemctl daemon-reload && sudo systemctl start jarvis`.
- **Claude (claude.ai)** lit l'état courant par le connecteur JARVIS, outil `jarvis_pilotage_lire` (lecture seule), plus par le connecteur Google Sheets.

## Tester (toujours avant de montrer)

**Quels bancs lancer (son retour du 24/11/2026 : « on passe la moitié du temps sur les bancs »)** : tester reste obligatoire, mais
pas tout, pas à chaque fois, et jamais en attendant à la fin.
